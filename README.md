# Freight_cost_simulator — 運送採算カルテ

運送原価を国交省「適正運賃」の積算要素(燃料費・人件費・減価償却費・安全確保費)に基づいてボトムアップで積算し、それを**月次の採算管理**につなげる分析ツール。合成データによるポートフォリオ作品。

## 現在の状態

| 層 | 内容 | 状態 |
|---|---|---|
| L0 | 合成データ基盤(運行実績・車両・ドライバー・顧客) | **実装済み** |
| L1.5 | 可視性ギャップの可視化 ★ | **実装済み** |
| L1.5+ | 荷主目線 × 業者目線のギャップ(積載率×集約数) ★ | **実装済み** |
| L2 | 感度分析(二層スライダー・トルネード・損益分岐点) | **実装済み** |
| L1 | 月次採算カルテ(4階層ドリルダウン・稼働率・全社ランキング) | **実装済み** |
| L4 | 経営レポート(顧客ポートフォリオ2×2・部署P/L・集中リスク表・貨物価値×運賃ギャップ) | **実装済み** |
| L3 | 交渉アクション化(交渉候補リスト・ステータス管理・自社標準単価表) | **実装済み** |
| — | 単発の原価計算(v0.1) | 実装済み・「運賃判断」タブに収容 |

**L0〜L4+L3、設計書に描いた全層が実装済み。**

v0.1は単発計算ツールとして動作したが、**毎月開く理由が構造的に存在しない**ことが判明した。v1.0ではこれを月次採算カルテとして再設計し、v0.1をその中の1機能として位置づけ直している。

### 中心的な結果

合成データの各コースに赤字の「真の原因」を仕込んでおき、切り分けロジックにはそれを見せずに運行実績だけから推定させ、事後に答え合わせしている。

| 視点 | 主因の的中率 |
|---|---|
| ① 売上と輸送費しか見えない場合 | **50.0%** |
| ② 原価ドライバーまで見える場合 | **91.7%** |

①が当たらないのはロジックの出来が悪いからではなく、**入力に原因を識別する情報が存在しない**ため。この非対称性が可視性の価値そのものであり、この作品の主張になっている。

**もう1つの結果(荷主目線×業者目線)**: 実務は特積(混載)だが荷主にはFTL(貸切)として請求している場合、物理積載率(荷主が体感しうる軸)と1運行あたりの集約案件数(業者だけが見える、実収益を決める軸)は別物であり食い違いが生まれる。合成データ上では、**「積載率は低いが集約数は多い」象限が全4象限中もっとも実際の粗利平均が高い**という結果が出た。荷主から見れば非効率に映りうるコースが、実は最も業者の利益に貢献している。

### L2で意識したこと

L2(感度分析)は当初、スライダーとトルネードチャートを並べるだけの構成で設計していた。実装直前に「現場でどう使うのか、の目線が抜けている。結論ありきのテーブルに見える」という指摘を受け、各画面に**現場での運用シナリオ**(毎月何をどう見て、次に何をするか)と**「次にすること」プロンプト**(他タブへの橋渡し)を明示的に埋め込む形に直した。診断結果を並べるだけでは「一回使ったきりで終わる」問題がより洗練された形で再発する、という反省による。

### 収益モデルの並存(既知の設計課題)

`月次カルテ`タブ(L1)・`経営レポート`タブ(L4)は`trip_orders`(業者目線の実収益、L1.5+で導入)を正として使う。一方`見えている世界/見えていない世界`タブ(L1.5)と`感度分析`タブ(L2)は`trips.revenue_yen`(積載率ベースの旧モデル、v1.0オリジナル)を使っており、**2つの収益モデルが並存している**。詳細と経緯は[docs/design.md](docs/design.md)のL1節を参照。将来的な統合は未着手。

### L4で分かったこと: 「価値相応の運賃」象限がほぼ空になる

貨物価値×運賃のギャップ分析で、運賃を貨物価値と意図的に無相関に生成したところ、**「運賃/貨物価値比率」が貨物価値の逆数にほぼ機械的に連動し、ほぼ全顧客が「高価値×低比率」または「低価値×高比率」のどちらかに集中する**という結果になった。バグではなく、「運賃が貨物価値を一切考慮していない」という設計意図そのものを定量的に裏付ける結果(価値に応じた値決めが機能していれば比率は価値によらず収束するはず)。詳細は[docs/design.md](docs/design.md)のL4節を参照。

### L3で分かったこと: 「不足額」だけでは交渉候補が0件になる

交渉候補の優先度を「目標粗利率(v0.1由来の10%)に対する不足額」だけで決めると、合成データでは全顧客が既に11.9〜13.5%の粗利率を確保しており、**不足額が全顧客で0円になり候補リストが機能しない**ことが実装時に判明した。優先度は「売上規模 × 前回改定からの経過月数」を主軸にし、不足額は加点要素に格下げした。これにより粗利が健全な期間でも、据え置き期間の長い大口顧客から優先的に交渉候補が挙がるようになった。また`negotiations`テーブルは当初コース単位のFKだったが、1コースを複数顧客が積み合わせる実態(L1.5+)を踏まえ顧客単位に作り直した(未使用のうちの変更だったためリスクなし)。詳細は[docs/design.md](docs/design.md)のL3節を参照。

## 中心的な問題設定

**売上責任を持つ部署が、輸送原価のドライバーを保有していない**という構造を扱う(実車手配が別部署の所管であるケース)。

輸送原価が壊れるパターンは4つあり、**それぞれ打ち手が全く異なる**。

| 壊れ方 | 打ち手 | 交渉相手 |
|---|---|---|
| 運賃が安い | 運賃改定交渉 | 荷主 |
| 積載率が低い | 帰り荷営業・配車統合 | 他部署(配車) |
| 拘束時間が長い | 荷待ち削減・条件見直し | 荷主 or 自社倉庫 |
| ドライバー別の燃費が悪い | 教育・車両更新 | 他部署(輸送) |

原価ドライバーが見えないと「粗利が悪い」は分かっても「だから何をするか」が選べない。本プロジェクトの問いは「原価をどう計算するか」ではなく、**「原価ドライバーが他部署にあるとき、採算責任をどう持つか」**である。

同種のツールが実運送事業者(自社で車とドライバーを持つ企業)向けに設計されているのに対し、**車を持たない側の採算可視化**を扱う点が差別化点。

## v1.0で答えられるようになる問い

- 今の情報量では何が判断できず、何が見えれば判断できるようになるのか
- 赤字コースの主因は上表4パターンのどれか。よって交渉相手は荷主か、他部署か
- 軽油が10円/L上がったら営業利益はいくら減るか。その影響はどこに集中しているか
- 燃料高騰を積載率の改善で打ち返せるか。打ち返せないならいくらの値上げが必要か
- 売上上位の顧客は、採算も良いのか
- 次に運賃交渉すべき顧客はどこか。いくら要求すべきで、根拠は何か

## 設計の特徴

同じ計算エンジンを2モードで切り替える。

- **支払い側モード**: 協力会社への支払運賃が適正原価を下回っていないか(過小支払いによる供給継続リスクの検証)。ノンアセット型元請にとってのリスク管理そのもの
- **交渉側モード**: 荷主への請求運賃に値上げ余地があるか

## セットアップ(初回のみ)

```bash
pip install -r requirements.txt
```

合成データを生成してDBへ投入する(18ヶ月・約9,100運行):

```bash
python -m src.synth.load_to_db
```

**2回目以降は`start_app.bat`をダブルクリックするだけでよい**(既定のブラウザが自動で開く)。停止はウィンドウを閉じるか`Ctrl+C`。

```bash
streamlit run app.py

```

## 使い方

- **「月次カルテ」タブ** — 粗利の月次推移、コース別月次サマリー(稼働率含む)、行クリックでコース→車両→ドライバー→個別運行と掘り下げるドリルダウン、車両別・ドライバー別の全社ランキング
- **「見えている世界 / 見えていない世界」タブ** — 的中率の対比、同一コース群の並置ビュー、誤選択コスト、コース別の要因分解
- **「荷主目線 × 業者目線」タブ** — 積載率×集約数の散布図(4象限)、象限ごとの実際の粗利、食い違いコース一覧
- **「感度分析」タブ** — 土台(燃料単価・人件費)/打ち手(値上げ率・積載率)の二層スライダー、全社への影響と集中度、トルネードチャート、コース別損益分岐点。画面ごとに現場運用シナリオと「次にすること」を明示
- **「経営レポート」タブ** — 部署P/Lサマリー(前年同月比)、顧客ポートフォリオ2×2(値上げ交渉/維持/育成/撤退検討)、集中リスク表、貨物価値×運賃のギャップ2×2
- **「交渉管理」タブ** — 交渉候補リスト(優先度順)、ステータス起票・更新(未着手/交渉中/合意/決裂/保留)、自社標準単価表(CSVダウンロード可)、`Freight_rate_hike_justification_template`への引き渡しテキスト生成
- **「運賃判断」タブ** — 単発の原価計算。車種・走行距離・拘束時間・高速代・モード・現在の運賃を入力して損益分岐運賃と適正原価を出す
- **「計算履歴」タブ** — 運賃判断の記録一覧

## データについて(重要)

**実データ・実企業名・実運賃・実車番・実ドライバー名は一切使用していない。** 車種別燃費・減価償却額、燃料単価・人件費単価・安全確保費率・目標利益率、コース名、運賃額はすべて仮置きの合成値であり、実績とは無関係である。

参考にした一次情報の出典(数値そのものは合成):

- 燃料単価: 資源エネルギー庁の燃料価格調査
- 人件費単価: 賃金構造基本統計調査(トラックドライバー職種)
- 積算要素の構成: 国土交通省「標準的運賃」「適正運賃」の考え方

匿名化の非交渉事項は [docs/design.md](docs/design.md) §6 に定義している。

## 技術構成

Streamlit + SQLite + pandas。チャートはAltair(Streamlit同梱のため追加依存なし、ブラウザ描画なので日本語フォントの問題も起きない)。

```
src/
├── common/      config(全パラメータ集約) / calendar / labels(表示名) / palette(検証済み配色)
├── synth/       generate(合成データ生成器、trip_orders含む) / load_to_db
├── analysis/    attribution(要因分解) / visibility(Lv1 vs Lv3) / perspective_gap(荷主×業者) / sensitivity(感度分析) / monthly(月次カルテ) / customer_portfolio(経営レポート) / negotiation(交渉管理) / data_access
├── ui/          visibility_gap(L1.5タブ) / perspective_gap(荷主目線×業者目線タブ) / sensitivity(感度分析タブ) / monthly(月次カルテタブ) / customer_portfolio(経営レポートタブ) / negotiation(交渉管理タブ)
├── cost_engine.py   原価積算(UI非依存の純粋ロジック)
└── db.py            スキーマ
```

配色は`dataviz`のvalidatorで実際に検証している。4主因それぞれに色を割り当てる案は all-pairs のCVD分離で不合格だったため、**エンコーディング自体を見直し**、色はLv1/Lv3の対比(2枠)のみに使い、主因はラベルで識別する構成にした(経緯は`src/common/palette.py`のdocstring)。
