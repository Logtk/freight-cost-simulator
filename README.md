# Freight_cost_simulator — 運送原価の「見えない部分」を可視化する採算カルテ

運送業務の売上責任を持ちながら実車手配は別部署が担う組織構造のもとで、原価が悪化した「真因」を4パターンに分解し、次の一手を判断可能にする月次採算分析ツールです。合成データによるポートフォリオ作品。

## 背景と解決したい課題（Why）

3PL(物流受託)企業の一営業所は、運送業務の売上責任を持つ一方で、実際に車両を手配する部署は別、という組織構造がよくあります。この場合、運賃・拘束時間・積載効率・ドライバー別燃費といった原価を左右するデータそのものが、日常業務の中で見えません。「利益が悪化している」という結果だけが降りてきて、原因が運賃なのか、配車の非効率なのか、荷待ちによる拘束時間の伸長なのか、ドライバー個々の運転特性なのかを切り分けられず、「だから何をすべきか」を判断できない、という構造的な空白があります。

この空白を埋めるツールを作る前に、市場に既にある類似製品を調査しました。その結果、同種のサービスを提供する企業が実際には2つの製品(単発の運賃シミュレーター/月額固定と、車両単位の月次採算カルテ/従量課金)を別々に売っており、前者は「滅多に発生しない問いに答えるツールなので開く理由がない」、後者は「毎月データが変わるから開く」という、精度やUIの差ではなく利用頻度の構造そのものが違う、という仮説にたどり着きました。最初に作った単発計算ツール(v0.1)を磨くのではなく、月次カルテを親とし単発計算をその中の1機能として位置づけ直したのは、この現場観察に基づく設計判断です。

## 誰のためのツールか、どう自分たちに応用するか

**対象読者**: 3PL・利用運送(ノンアセット)事業者で、売上責任は持つが実車手配は協力会社・他部署任せという組織構造の管理職・企画担当。この「売上責任と原価ドライバーが分離している」という構造は3PLに限らず、一次請けが実作業を協力会社に委託するBPO・警備・清掃といった労働集約型サービス業全般にも当てはまり得ると考えています。

**応用方法**: `src/synth/generate.py`が返す`frames`(customers/vehicles/drivers/courses/trips/trip_orders)と同じ列構成のDataFrameを用意すれば、`load()`関数以降のL1〜L4のロジックはコード変更なしでそのまま流用できます。燃料単価・人件費単価は感度分析タブからUI上で書き換え可能なので、自社の実際の単価への差し替えもコードに触れずに試算できます。実データを持たない段階でも、`src/common/config.py`の`Settings`(コース数・車両数・波動係数)を自社の事業規模に近い値に変えるだけで、より実感の持てる合成データでの検証が可能です。

## 機能概要とアーキテクチャ（What / How）

Streamlit + SQLite + pandas(可視化はAltair)によるシングルユーザー分析ツールです。5段階のレイヤーで構成しています。

- **L0(ファクトデータ基盤)**: `trips`(運行実績)・`vehicles`・`drivers`・`customers`・`cost_settings_snapshots`(計算時点の単価設定を保存し、燃料単価等が変わっても過去の月次比較が壊れないようにするテーブル)
- **L1(月次採算カルテ)**: コース→車両→ドライバー→個別運行への4階層ドリルダウン
- **L2(感度分析)**: 燃料単価・人件費の変動、値上げ・積載率改善の効果をスライダーで試算。土台(外部環境)スライダーと打ち手(自社の努力)スライダーを分離し、「打ち返せない領域」を正直に示す設計
- **L4(経営レポート)**: 顧客ポートフォリオ2×2、特定顧客への売上集中リスク、貨物価値×運賃のギャップ分析
- **L3(交渉アクション化)**: 運賃交渉が必要な顧客を優先度付きでリストアップし、`Freight_rate_hike_justification_template`へのコピー&ペースト用テキストを生成

**検証設計の核**: 合成データ生成時に各コースへ赤字の「真因」をground truthとして仕込み、切り分けロジックはそのground truthを一切参照せず運行実績だけから主因を推定 → 事後に答え合わせをして的中率を測定するという検証構造を組みました。結果、「売上と運賃しか見えない」状態(Lv1)での的中率は50.0%、原価ドライバーまで見える状態(Lv3)では91.7%——**+41.7ptという差そのものが、可視性を高めることの価値の定量化**になっています。単なるダッシュボードではなく、「見える化にどれだけの意味があるか」を検証するための実験設計です。

### 動かし方

```bash
pip install -r requirements.txt
python -m src.synth.load_to_db   # 合成データ生成(18ヶ月・約9,100運行)
streamlit run app.py             # または start_app.bat をダブルクリック
python -m pytest tests/ -v       # テスト(インメモリDBのみ使用)
```

## 現在のステータスと直面している課題（Current Status & Technical Challenges）

L0〜L4・L3の全レイヤーが実装完了し、テストは全件パスしています。ポートフォリオとしては「動くもの」の段階を超えていますが、実装を進める過程で意図的に解決を保留している構造的な課題が2つあります。

**1. 収益モデルの二重構造(未統合)**

実装の過程で、`trips.revenue_yen`(車両の積載率をベースにした収益モデル、初期の実装が採用)と、`trip_orders`の合計(荷主ごとの実収益を積み上げた収益モデル、実務知見「集約数が実収益を決める」を反映して後から導入)という、2つの並行した収益モデルが存在していることに気づきました。荷主目線と業者目線のズレを可視化するこのツールの設計思想上、後者の方が実態に近いと判断していますが、感度分析(L2)の的中率検証は前者のモデルで既にキャリブレーション済みのテストを持っています。ここで無理に一本化すると検証済みのロジックとテストを壊すリスクがあるため、**「両モデルが並存する」という事実自体を設計書に明記した上で、統合を将来課題として保留する**という判断をしています。分析ツールの内部に複数の収益モデルが共存すること自体が、実務における「見え方の違い」の縮図になっている、とも捉えています。

**2. 稼働率指標の簡易化**

車両の稼働率は「運行日数 ÷ 当月営業日数」という簡易指標で計算しています。合成データ生成器が「車両の稼働可能日」という概念(車検・整備等による非稼働日)を持たないため、全車両が常時稼働可能という前提の近似値です。実データを接続する段階では、車両マスタに稼働可能日カレンダーを追加する必要があると認識しています。

## 今後の展望（Next Steps）

- **貨物価値を組み込んだ運賃モデルへの拡張**: 運賃を貨物価値と無相関に生成した合成データを分析したところ、「運賃/貨物価値比率」が貨物価値の逆数にほぼ機械的に連動し、全顧客が「高価値×低比率」か「低価値×高比率」のどちらかに集中する(価値相応の象限がほぼ空になる)という結果が出ました。これは「現在の運賃が貨物価値を考慮していない」という設計上の前提そのものを裏付ける結果です。貨物価値を変数に組み込んだ動的な運賃モデルへの拡張は、強いエンジニアリングとの協業で取り組みたい領域です。
- **実データ連携**: 現状はSQLite+合成データで完結していますが、実際のWMS/TMSデータと接続する段階では、DB設計(特にL0のスキーマ)をどこまで流用できるか検証が必要です。
- **交渉ロジックの高度化**: L3の交渉候補生成は現状ルールベースですが、過去の交渉履歴データが蓄積された段階で、生成AIを使った交渉トークスクリプトの自動下書きや、類似案件からの相場感提示へ発展させたいと考えています。

## データについて（重要）

実データ・実企業名・実運賃・実車番・実ドライバー名は一切使用していません。車種別燃費・減価償却額、燃料単価・人件費単価・目標利益率、コース名、運賃額はすべて仮置きの合成値であり、実績とは無関係です。参考にした一次情報の出典(数値そのものは合成):

- 燃料単価: 資源エネルギー庁の燃料価格調査
- 人件費単価: 賃金構造基本統計調査(トラックドライバー職種)
- 積算要素の構成: 国土交通省「標準的運賃」「適正運賃」の考え方
