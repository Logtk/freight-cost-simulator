# 輸送原価データ 可視性アセスメント

## このドキュメントの目的

売上責任を持つ営業所が、輸送原価のドライバーを**どこまで見えているか / 見えていないか**を項目単位で棚卸しする。

出発点は「輸送原価が壊れる4パターン(運賃が安い/積載率が低い/拘束時間が長い/ドライバー別の燃費が悪い)のうちどれが起きているか、自部署からは把握できていない」という認識である。実車手配が他部署の所管であるため、原価ドライバーは他部署のオペレーションとシステムの中にある。

**ここが本プロジェクトの主題である。** 原価計算の精緻化ではなく、「原価ドライバーが他部署にあるとき、採算責任をどう持つか」を扱う。

### なぜ棚卸しが先か

4パターンは**打ち手が全く異なる**。

| 壊れ方 | 打ち手 | 交渉相手 |
|---|---|---|
| 運賃が安い | 運賃改定交渉 | 荷主 |
| 積載率が低い | 帰り荷営業・配車統合 | 他部署(配車) |
| 拘束時間が長い | 荷待ち削減・条件見直し | 荷主 or 自社倉庫 |
| ドライバー別の燃費が悪い | 教育・車両更新 | 他部署(輸送) |

見えていない状態でこの4つのどれに労力を割くかを決めるのは、**賭け**になる。可視性の欠如の本当のコストはここにある。「粗利が悪い」は分かっても「だから何をするか」が選べない。

## 1. 可視性の成熟度モデル

現状と目標を同じ尺度で語るための段階定義。

| Lv | 状態 | できる判断 |
|---|---|---|
| **0** | 輸送費が総額でしか見えない | 全体が黒字か赤字か |
| **1** | コース別・顧客別に輸送費が分かる | どの取引が低採算か |
| **2** | 運行単位に分解できる | 特定の運行が異常か、傾向か |
| **3** | 原価ドライバー(積載率・拘束時間・燃料)が分かる | **4パターンのどれで壊れているかの切り分け** |
| **4** | 車両別・ドライバー別に分かる | 個別の改善対象の特定 |

**Lv3が分水嶺。** ここを超えないと打ち手が選べない。Lv4は運用改善のための粒度であり、経営判断としてはLv3で足りる場面が多い。

現状の自己評価: **要記入(Lv___)**

## 2. 項目別 棚卸しシート

「有無」列の記入凡例: `◎`=自部署で見えている / `○`=他部署にあり入手可能 / `△`=あるが粒度不足 / `▲`=他部署にあるが未共有 / `×`=そもそも測っていない / `?`=不明

| # | 項目 | 想定保有者 | 有無 | 粒度 | これが分かると判断できること |
|---|---|---|---|---|---|
| 1 | 顧客別・コース別売上 | 自部署 | `?` | | 採算評価の分母。これが無いと何も始まらない |
| 2 | 輸送費 総額 | 自部署 | `?` | | 全体の黒赤のみ。内訳が無いと打ち手不明 |
| 3 | コース別 輸送費 | 配車部署 | `?` | | どのコースが低採算か(Lv1到達の条件) |
| 4 | 運行回数 | 配車部署 | `?` | | 1運行あたり単価の算出 |
| 5 | 使用車格(2t/4t/10t) | 配車部署 | `?` | | 車格が過大でないか(小口を大型で運んでいないか) |
| 6 | 実走行距離 | 配車部署 | `?` | | 計画距離との乖離。遠回り・重複配送の検知 |
| 7 | **積載率** | 配車部署 | `?` | | **「運賃値上げでは解決しない」領域の切り分け。帰り荷営業・配車統合の余地**(空車回送距離ベースの「実車率」とは別概念。積載率=容量に対する充填度、実車率=走行距離に対する実車走行の割合) |

| 10 | **待機時間の内訳(自社倉庫側/納品先側)** | 配車部署 | `?` | | **責任の所在。自社倉庫側なら自部署の改善課題、納品先側なら荷主交渉の根拠** |
| 11 | 実燃料消費量 | 輸送部署/協力会社 | `?` | | 燃料費の実額。公称燃費との乖離 |
| 12 | 高速代(実費) | 配車部署 | `?` | | 実費パススルーの妥当性 |
| 13 | 車両別実績 | 輸送部署 | `?` | | 老朽車の燃費悪化・更新判断(Lv4) |
| 14 | ドライバー別実績 | 輸送部署 | `?` | | 教育対象の特定(Lv4)。※人事評価への転用は慎重に |
| 15 | 協力会社別 支払単価 | 配車部署 | `?` | | 支払いが適正原価を下回っていないか(供給継続リスク) |
| 16 | 前回運賃改定日(顧客別) | 自部署/営業 | `?` | | 交渉タイミングの優先順位付け |

**太字の4項目(7・8・9・10)が最優先。** これらがLv3の到達条件であり、4パターンの切り分けを直接可能にする。

### 項目10について

`待機時間の内訳`は一覧の中で最も見落とされやすく、かつ最も価値が高い。拘束時間が長いという事実だけでは打ち手が決まらないが、**それが自社倉庫側の待機なのか納品先での荷待ちなのかで、責任の所在と交渉相手が変わる**。前者なら自部署のオペレーション改善課題であり、後者なら荷主への条件交渉の根拠になる。総拘束時間だけを取って満足しないこと。

## 3. 他部署に確認する際の問いの立て方

「データをください」ではなく、**何を判断したいかを先に示す**。相手の作業を増やす依頼になるため、目的が共有されていないと優先されない。

推奨する順序:

1. **目的の共有** — 「顧客別の採算を見て、運賃交渉すべき先を絞りたい。ただ今は粗利が悪い理由が運賃なのか積載率なのか分からず、打ち手を選べていない」
2. **既存の帳票から入る** — 新規のデータ抽出を依頼する前に、既に作られている帳票・日報・配車表に何が載っているかを見せてもらう。**多くの場合、すでに存在するが共有されていないだけ**である
3. **粒度の確認** — 月次集計しか無いのか、運行単位の元データが残っているのか。集計値しか無い場合、元データが破棄されているのか単に集計後に見ていないだけなのかを分ける
4. **測っていない項目の切り出し** — `×`が付いた項目について、測るコスト(手間)と分かる価値を並べて相談する。**全部測る必要はない**。項目7・9・10が取れれば大半の切り分けはできる

### 記入後に判明することの想定

| パターン | 主題 | 打ち手 |
|---|---|---|
| `▲`が多い(あるが未共有) | 組織のサイロがP/L可視性を殺している | データ連携の仕組み化・権限設計 |
| `×`が多い(測っていない) | 測っていないものは改善できない | 計測設計。何をどこまで測るかの取捨選択 |
| 混在 | 上記の両方が並行して必要 | `▲`は交渉、`×`は計測設計に振り分ける |

現時点の想定は「混在」である(項目によって状況が異なるため)。

## 4. 本プロジェクト(ダッシュボード)への接続

このシートの記入結果が、[design.md](design.md) のL0(ファクトデータ基盤)の設計を確定させる。

- `◎○▲` の項目 → 実データで取得しうる想定。ダッシュボードの入力項目として設計する
- `×?` の項目 → **合成データでは「もし取れたら何が見えるか」を示す役割**を持たせる。取得価値の提示そのものが分析になる

つまり合成データ版は、単なるデモではなく**「この可視性を手に入れたら、何が判断できるようになるか」の実証**として機能する。可視性が無い状態(Lv0〜1)と、ある状態(Lv3)を並べて見せる二層ビューが、この作品の中心的な主張になる。
