# 設計書: 運送採算カルテ(Freight_cost_simulator)

## 0. このドキュメントの位置づけと方針転換

v0.1は「運行条件を入力すると適正原価を算出する」単発計算ツールとして構築された。実際に動かした結果、**毎月開く理由が構造的に存在しない**ことが明らかになった。詳細な経緯と競合調査は [competitive_analysis.md](competitive_analysis.md) を参照。

本設計書は、プロジェクトを以下のように再定義する。

| | v0.1(実装済み) | v1.0(本設計書) |
|---|---|---|
| 主対象 | 単発の原価計算 | **月次の採算管理** |
| データ | マスタのみ(実績なし) | **運行実績ファクト(合成データ)** |
| 粒度 | コース | **コース → 車両 → ドライバー → 個別運行** |
| 問い | 「このコースの原価は?」 | 「**どこで利益が失われているか。何が効くか**」 |
| v0.1の扱い | プロジェクト全体 | 全体の中の1機能(運賃判断タブ) |

**v0.1は捨てない。** `src/cost_engine.py` の積算ロジックはそのまま採算計算の中核として使う。破壊的変更は行わず、既存の7件のテストは通り続ける設計とする。

### 成果物としての性格

本プロジェクトは**合成データによるポートフォリオ作品**である。実データ・実企業名・実運賃は一切使用しない(§6の非交渉事項)。

想定読者はコンサルティングファーム/経営層であり、彼らが評価するのは操作性ではなく分析設計の構造である。したがって優先度は「感度分析・ポートフォリオ分析 > 月次カルテの作り込み」となる(§5)。

## 0.5 中心的な主張: 可視性の欠如そのものが主題

設計を進める中で、より本質的な論点が判明した。**売上責任を持つ営業所が、輸送原価のドライバーを保有していない**という構造である(実車手配が他部署の所管)。

このため、輸送原価が壊れる4パターン(運賃が安い/積載率が低い/拘束時間が長い/ドライバー別の燃費が悪い)のうちどれが起きているかを、売上責任者が把握できない。そして**この4つは打ち手が全く異なる**(運賃改定/帰り荷営業/荷主への条件交渉/ドライバー教育)。

結果として「粗利が悪い」は分かっても「だから何をするか」が選べない。これが可視性の欠如の実質的なコストである。

よって本プロジェクトの問いは以下のように再定義される。

- ❌ 「運送原価をどう積算するか」(計算の問題。電卓の精度競争になる)
- ✅ **「原価ドライバーが他部署にあるとき、採算責任をどう持つか」**(組織とデータの問題)

後者は部門を横断して原価ドライバーとP/Lを接続する営みであり、CLOの職務そのものの縮図である。また、同種の既存ツールが実運送事業者(自社で車とドライバーを持つ企業)向けに設計されているのに対し、**車を持たない側の採算可視化**は空白領域である。これが本プロジェクトの差別化点となる。

### 二層ビュー(この作品の中心的な見せ方)

| 層 | 中身 | 対応する成熟度 |
|---|---|---|
| **今見えている世界** | 売上 − 輸送費(総額一本) = 粗利 | Lv0〜1 |
| **見えていない世界** | その輸送費の内訳。4パターンのどれで壊れているか | Lv3 |

**この2つの差分そのものを主役にする。** 合成データは単なるデモではなく「この可視性を手に入れたら何が判断できるようになるか」の実証として機能させる。

可視性の段階定義(Lv0〜4)と、項目別の棚卸しシートは [data_visibility_assessment.md](data_visibility_assessment.md) に分離した。

**なおシートの記入は本リポジトリの実装をブロックしない。** 記入が必要なのは「実務で他部署からデータを取る」トラックであり、ポートフォリオ版は合成データで4パターンすべてを再現するため独立して進められる。両者は目的が異なる別トラックとして扱う。

## 1. 設計の前提(調査で確定した事実)

実装に入る前に確認した事実を記録する。これらは設計判断の根拠であり、実装時に前提が崩れていないか確認すべき項目でもある。

1. **ファクトデータがどこにも存在しない**。`calculations`テーブルは0行、`.gitignore`が`data/*.db`を除外しているためDBはコミットされていない。→ **合成データ生成器はオプションではなく土台**である。
2. **`Sales_quote_optim`との結合は行わない**。同案件の`quotes`テーブルとの間に共有ディメンションが1つも存在しない(顧客・エリア・車両・日付すべて不在)。DBファイルも別。かつ同案件の`total_cost`はエリア×重量帯タリフ由来で、本案件のボトムアップ原価とは**そもそも比較可能な数値ではない**。→ **売上側は本案件内に自前で持つ**。これが本設計における最大の判断である。
3. **車両インスタンスとドライバーの概念がない**。`vehicle_types`は車格(2T/4T/10T)のみで、車番・ドライバーのマスタもFKも存在しない。→ ドリルダウンのために新設が必要(§3)。
4. **`calculations`が計算時点の設定値を保存していない**。燃料単価を更新すると過去行が再現不能になる。単発計算では無害だが、**月次で時系列比較する採算カルテでは致命的**。→ スナップショット機構を新設(§3)。
5. **損益分岐運賃が変動費のみで定義されている**(`src/cost_engine.py:132`、燃料費+高速代。人件費・減価償却を除外)。定義として成立するが、採算カルテの文脈では誤読を招く。→ 「変動費ベース」と明示ラベルし、全部原価ベースの分岐点を併記する(§4のL2)。

## 2. 分析の全体構造

層の番号は役割の識別子であり、実装順とは一致しない(実装順は§5)。


### 3.2.1 `synth_course_truth` — 主張を検証可能にする仕掛け(実装時に追加)

設計当初には無かったが、実装時に中核となった要素。

```sql
-- 合成データのground truth。実データには一切存在しない。
CREATE TABLE IF NOT EXISTS synth_course_truth (
    course_id INTEGER PRIMARY KEY REFERENCES courses(course_id),
    loss_pattern TEXT NOT NULL,   -- healthy/low_rate/low_loaded_ratio/long_binding/poor_fuel
    severity REAL NOT NULL,
    confounder_pattern TEXT       -- 副次要因(交絡)
);
```

`Volume_forecast_portfolio` は真の需要 `true_demand` を生成しておきながらモデルには渡さず、観測値だけで学習させることで「欠品が予測を歪める」ことを実証している。**同じ構造を可視性ギャップに適用する。**

- 生成時に各コースへ赤字の真因を仕込み、正解として保存する
- 切り分けロジック(`src/analysis/attribution.py`)は**この表を一切参照せず**、運行実績だけから主因を推定する
- 事後に突き合わせて**的中率を測る**

これにより「Lv1の情報では主因を当てられないが、Lv3の情報があれば当てられる」を数値で示せる。可視性の価値の定量化そのものである。

**交絡を意図的に混ぜる**のも要件である。全コースが単一要因できれいに説明できると切り分けが自明になり、的中率という指標が意味を失う。`confounder_pattern` により副次要因を軽度で付与し、「当たるが完璧ではない」水準を保つ。

実装時点の実測値: **Lv1 50.0% / Lv3 91.7%(+41.7pt)**。この水準はテストで下限を固定している(`tests/test_synth_and_visibility.py`)。

### 3.3 `actual_fuel_liters` を持つ理由

車格の公称燃費から計算するだけなら列は不要だが、**実燃料消費量を持つと「同じコース・同じ車格でもドライバーによって燃費が違う」という分析ができる**。これはドライバー別採算の説得力を大きく左右する要素で、かつ運送業の実務で実際に管理されている指標である。NULL許容とし、NULLの場合は車格の公称燃費から推定する(合成データでは意図的にドライバー別のばらつきを与える)。

### 3.4 原価計算の再利用方針

`src/cost_engine.py:calculate_cost()` は現状「計画値(courses)」を入力に取るが、これを**実績値(trips)も入力に取れる**よう拡張する。関数シグネチャの破壊的変更は避け、`CostInput`に実績由来の値を渡す形にする(既存の呼び出し元とテストは無変更で動く)。

ドライバー個別の時間単価がある場合は`cost_settings`の全社一律単価より優先する、という上書き規則を追加する。

## 4. 機能仕様

### L1: 月次採算カルテ(実装済み、2026-08-02)

**目的**: 毎月開く理由を作る。先月の実績が確定するたびに見に行く画面。

- コース別の月次サマリー表: 売上 / 原価 / 粗利 / 粗利率 / 運行回数 / 稼働率
- 粗利の月次推移(時系列、全期間)。**単月の絶対値ではなくトレンドで悪化を捉える**ことを主眼にする
- ドリルダウン: コース → 車両 → ドライバー → 個別運行の4階層。`st.dataframe(on_select="rerun", selection_mode="single-row")`で行クリックを検知し、選択キーを`st.session_state`に保持して次階層の表を下に段階的に表示する方式(`Inv_mgmt_optim/index.html:594`の動線をStreamlitに移植)。上位階層の選択が変わったら下位の選択は破棄する
- 稼働率: 「運行日数 ÷ 当月営業日数」の簡易指標。**車両が実際に稼働可能だった日数というデータを合成データが持たない**ため、全車両が常に稼働可能だったと仮定する近似値であることをUI上に明記
- 車両別・ドライバー別の採算ランキング(全社・コース横断)

**収益モデルの並存(設計上の懸念、実装時に判明)**: `src/analysis/monthly.py`は`trip_orders`(業者目線の実収益、L1.5+で導入)を正として使う。既存のL1.5(`attribution.py`/`visibility.py`)とL2(`sensitivity.py`)は`trips.revenue_yen`(積載率ベースの旧モデル、v1.0オリジナル)を使っており、**2つの収益モデルが並存する状態になっている**。本人の実務知見(集約数が実際の利益を決める)を踏まえると`trip_orders`ベースの方が実態に近く、月次の実績を扱うL1ではこちらを採用した。ただしL1.5の的中率検証(50.0%/91.7%)とL2の感度分析は`trips.revenue_yen`ベースで既にキャリブレーション済みのテストを持っており、今回はそちらを触っていない。**将来的にL1.5・L2を`trip_orders`ベースへ移行するかどうかは未決定の課題として残る。**

### L2: 感度分析 ★経営に刺さる核心①(実装済み、2026-08-02)

**目的**: 外部環境の変動に対する自部署のリスクexposureを数値で言語化する。

**設計の訂正(実装直前に判明)**: 当初案(このセクション初版)はスライダーとトルネードチャートを「分析機能」として並べるだけの構成だった。実装直前に「これを現場でどう使うのか、の目線が抜けている。結論ありきのテーブルに見える」という指摘を受けた。振り返ると、`PATTERN_ACTIONS`のような固定の対応表(主因→打ち手→交渉相手)や、L1.5・L1.5+の診断結果は、分類・ラベル付けで止まっており「それを見た後、現場の人間が具体的に何をするか」を示していなかった。L1(月次で開く理由)とL3(分析を行動に変える出口)を後回しにしたままL2のような診断層だけを積み増すと、v0.1を作り直した理由(「一回使ったきりで終わる」)がより洗練された形で再発する。

対応として、L2の各画面に**現場での運用シナリオ**(毎月何をどう見て、次に何をするか)と**「次にすること」プロンプト**(他タブへの橋渡し)を明示的に埋め込んだ。これはL1・L3の代替にはならないが、L2単体が「使う理由」を持てるようにする最低限の橋渡しとして機能する。次の実装(L1)を後回しにし続けないことも合わせて合意した。

- **二層スライダー**: 土台(燃料単価・人件費単価、自社では動かせない) / 打ち手(値上げ率・積載率改善、自社で動かせる)。`Sales_slip_ocr_optim/docs/strategy_options.md`§4の方法論を踏襲。この分離により「外部環境の悪化を自社の努力でどこまで打ち返せるか」という代替関係を可視化する
- **全社への影響**: 現状の営業利益とシナリオ後の営業利益を並べ、**「このシナリオで営業利益の○%が失われ、そのうち○%は特定Nコースに集中している」という一文を自動生成**する(`concentration_summary`)
- **トルネードチャート**: 4レバーを現在のスライダー位置から単独で±振り、全社営業利益への影響幅でランキング。土台/打ち手を色分け(既存の2枠パレットをこのタブ限定で意味を変えて再利用)
- **損益分岐点分析**: コース別に、変動費ベース(燃料費+高速代)と全部原価ベース(+人件費+車両償却)の2本の分岐点運賃を現行運賃と並べる。土台スライダーの値が分岐点にも反映される(前提5への対応)

### L1.5: 可視性ギャップの可視化 ★この作品の主張の核

**目的**: 「見えていない状態のコスト」を金額で示す。§0.5の二層ビューを実装する層。

- **並置ビュー**: 同じ月の同じコース群について、Lv0〜1の情報だけで見た場合(売上 − 輸送費総額)と、Lv3の情報で見た場合(4パターンに分解)を左右に並べる
- **切り分け表**: コース別に「赤字の主因はどれか」を4パターンで判定し、打ち手と交渉相手を併記する。ここが「粗利が悪い」から「何をするか」への変換点になる
- **打ち手の誤選択コスト**: 主因が積載率であるコースに運賃交渉を仕掛けた場合、どれだけの労力が空振りするかを試算する。可視性の欠如が招く**具体的な損失の形**を示す
- 成熟度レベル(Lv0〜4)の現在地表示。`data_visibility_assessment.md`の記入結果と接続する

### L1.5+: 荷主目線×業者目線のギャップ(実装時に追加、2026-07-31)

**実装のきっかけ**: v1.0(`loaded_ratio`による物理積載率モデル)を実際に動かしてフィードバックを求めたところ、本人から「実務は特積(混載)だが荷主にはFTL(貸切)として請求している。1台のトラックに何案件積めるかでコストは変わる」という業務知見が出た。当初はこれを機に既存モデルを**置き換える**プランを立てたが、本人から「荷主目線と業者目線で全く変わってくる。既存のものも残してほしい。このギャップが生み出す認識の相違を明らかにすること、コンフリクトから両社の検討余地が見えてくる」と訂正が入った。

**2軸の整理**:

| 軸 | 何を表すか | 誰の視点 |
|---|---|---|
| 物理積載率(`loaded_ratio`、既存) | トラックの中身がどれだけ詰まっているか | 荷主が体感しうるナイーブな専有効率の軸 |
| 集約案件数(`orders_per_trip`、追加) | 1回の運行に何件のFTL請求案件を積み合わせられたか | 業者だけが見えている、実収益を決める軸 |

この2軸は独立に動きうる(1件の大口で満載=積載率高だが薄利、小口5件集約=積載率中でも業者は儲かる、等)。**この乖離が生まれるコースこそが、情報開示の要否・値決め交渉の検討余地になる。**

**データモデル**: `trip_orders`テーブルを新設(`trip_id`→`trips`のFK、`customer_code`、`ftl_rate_yen`、`requested_service`。L4実装時に`cargo_value_yen`を追記)。`trips`側は無変更(既存の`revenue_yen`・`customer_code`・`loaded_ratio`をそのまま荷主目線モデルとして使い続ける)。各案件の単価は積み合わせ相手が何件いようと一定(=積み合わせても値引きしない実態)とし、コースの標準原価にマークアップを乗せて独立に付与する。

**相関設計の落とし穴(実装して分かった要点)**: `orders_per_trip`を`loaded_ratio`に相関させる際、トリップ単位でノイズを加えるだけだと、1コースあたり数百件のトリップを平均した時点で大数の法則によりノイズが打ち消し合い、**コース集計後の相関が設計値(0.2〜0.4)より大幅に強く出てしまう**(実測でtrip単位corr 0.38 → コース単位corr 0.99まで見かけ上増幅する現象を確認した)。相関付けは「コース単位で1回だけ」行い、トリップ単位のノイズは別途小さく加える方式に修正した。

**分析結果(合成データによる試算)**: 4象限それぞれにコースが分布し、**「積載率は低いが集約数は多い」象限が全4象限中もっとも実際の粗利平均が高い**という結果が出た(荷主から見れば非効率に映りうるコースが、実は最も業者の利益に貢献している)。これは単なる動作確認を超えて、この分析軸自体の有用性を裏付ける結果になっている。

**UI**: 新規タブ「荷主目線 × 業者目線」。積載率×集約数の散布図(4象限、中央値で分割)、象限ごとの平均粗利、食い違い象限のコース一覧。配色は新規カテゴリカルパレットを起こさず、既存の`palette.py`のSTATUS(good/warning/critical)を流用する。

### L4: 経営レポート ★経営に刺さる核心②(実装済み、2026-08-02)

**目的**: 視座を現場の原価管理から経営のポートフォリオ判断へ上げる。

- **顧客ポートフォリオ 2×2**: 売上規模(横) × 粗利率(縦)で顧客を配置し、4象限に「値上げ交渉」「維持」「育成」「撤退検討」を割り当てる(全期間の集計、単月ノイズを避ける)。配色は新規パレットを起こさず`palette.py`のSTATUS(good/warning/critical)を流用し、4象限中2つ(値上げ交渉・育成)は同じwarning色にして位置とラベルで区別する(`perspective_gap.py`と同じ判断)
- **部署P/Lサマリー**: 売上・原価・粗利・粗利率(月選択式)と前年同月比。18ヶ月分の合成データでは前年同月が無い月もあるため、無い場合は「前年同月比は表示できない」と明示する
- **集中リスク表**: 上位顧客への売上依存度と、その顧客の採算を並べる。「売上の30%を占める顧客が最も低採算」という状態を可視化する。`Shipper_rate_negotiation`で扱った高依存リスクの論点と接続する
- **貨物価値×運賃のギャップ(3つ目のギャップ)**: 今のモデルは運賃を距離・車格・拘束時間からしか決めておらず、貨物の経済価値(業種別に数万円〜数千万円のレンジ、対数一様分布で抽選)を一切見ていない。案件ごとの`cargo_value_yen`(合成、`ftl_rate_yen`とは意図的に無相関)と運賃/貨物価値比率を顧客単位で集計し、4象限で可視化する。本人判断により顧客ポートフォリオ2×2とは**別の2×2として並置**した(1つの散布図に3軸目を詰め込むと読み取りにくくなるため)

**実装して分かったこと(重要)**: 運賃(`ftl_rate_yen`)を貨物価値(`cargo_value_yen`)と意図的に無相関に生成した結果、「運賃/貨物価値比率」は貨物価値の逆数にほぼ機械的に連動する(比率の分子である運賃の分散が、分母である貨物価値の分散よりはるかに小さいため)。そのため中央値で4分割すると、**全顧客が「高価値×低比率」または「低価値×高比率」のどちらかに集中し、「価値相応」の2象限にはほとんど誰も入らない**という結果になった。これはバグではなく、「運賃が貨物価値を一切考慮していない」という設計意図そのものを定量的に裏付ける結果である(価値に応じた値決めが機能していれば、比率は価値によらず一定水準に収束し、4象限に分散するはず)。

### L3: 交渉アクション化(実装済み、2026-08-02)

**目的**: 分析を行動に変える出口。同時に、月次で開く2つ目の理由(交渉の進捗確認)を作る。

**設計の訂正1: 交渉相手はコースではなく顧客**。`negotiations`テーブルはL0作成時点で`course_id`をFKに持っていたが、1コースを複数顧客が積み合わせる実態(L1.5+)があるためコース単位では交渉相手が一意に決まらない。テーブルは未使用のまま残っていたため、破壊的変更のリスクなく`customer_code`キーへ作り直した。

**設計の訂正2: 「不足額」だけでは候補が0件になる**。当初案通り「目標粗利率に対する不足額」だけで優先度を決めると、v0.1由来の`TARGET_PROFIT_RATE`(10%)に対して合成データの全顧客が既に11.9〜13.5%の粗利率を確保しており、**不足額が全顧客で0円になり候補リストが機能しない**ことが実装時に判明した。優先度を「**売上規模 × 前回改定からの経過月数**」を主軸にし、不足額があれば加点する方式に変更した。要求増額目安も、不足額だけでなく「経過月数に応じた緩やかな据え置き改定分」(年率2%を月数按分)を土台に加えることで、粗利が健全な期間でも意味のある金額を返せるようにした。

- **交渉候補リストの自動生成**: `build_candidates()`。優先度 = 売上規模×経過月数+不足額×100。常に差が付く2軸(売上規模・経過月数)を主軸にすることで、不足額が0の期間でも機能する
- **要求額の算出**: 据え置き改定分(年率按分)+ 目標粗利率への不足額
- **交渉ステータス管理**: `negotiations`テーブル(顧客単位)。未着手/交渉中/合意/決裂/保留、次回見直し日、メモ
- **自社標準単価表**: `build_standard_rate_sheet()`。コース諸元から構造的に期待される標準単価と現行運賃を並べる(`attribution.py`の`expected_values()`を再利用)。CSVダウンロード可
- **`Freight_rate_hike_justification_template`への数値受け渡し**: `format_handoff_text()`でコピー&ペースト用のテキストブロックを生成するに留める。**他プロジェクトのフォルダへの直接書き込みは行わない**(プロジェクト間の越権を避けるため。CLAUDE.mdの「各案件フォルダは自己完結」の原則にも合致)

## 5. 優先順位ロードマップ

```
可視性棚卸し(data_visibility_assessment.md記入) [実務トラック・独立]
   → L0 ✅ → L1.5 ✅ → L1.5+ ✅ → L2 ✅(感度分析、現場運用シナリオ付き) → L1 ✅(月次カルテ)
   → L4 ✅(経営レポート。3つ目のギャップ=貨物価値×運賃を並置) → L3 ✅(交渉管理)

**2026-08-02、L0〜L4+L3の全層が実装完了した。** 次のフェーズは機能追加ではなく、ポートフォリオとしての仕上げ(GitHub公開準備・匿名化最終チェック)になる。
```

**棚卸しを最初に置く理由**: L0でどの項目を実データ想定とし、どの項目を「取得価値の提示」に留めるかが、棚卸しの結果で決まる。ここが未確定のまま生成器を書くと、実務と接続しない合成データになる。

**L1.5をL2より前に置く理由**: 可視性ギャップは本作品の中心的な主張であり(§0.5)、かつL0のファクトがあれば集計のみで実装できる。感度分析は「見えるようになった後」の分析なので、順序としては後になる。

**L2をL1より前に置いた判断の見直し(2026-08-02)**: 当初は「感度分析は集計済みデータが少量あれば成立し、ポートフォリオとしての訴求が最も高い」という理由でL2を先に置いた。実装直前に「現場でどう使うのかの目線が抜けている、結論ありきのテーブルに見える」という指摘を受け、L2自体には現場運用シナリオを埋め込んで対応したが(§4 L2節参照)、**根本的にはL1(月次で開く理由)を後回しにし続けるべきではない**という結論に至った。次の実装はL4ではなくL1とする。

ただし**L0のファクトデータが無ければどちらも動かない**ため、L0は例外なく最初に完成させる。

## 6. 匿名化の非交渉事項

以下は議論の対象とせず、無条件で守る。

- 実データ・実企業名・実運賃・実車番・実ドライバー名を一切使用しない
- 顧客は`顧客A`〜`顧客F`等の匿名ラベル、車両は`車両01`〜、ドライバーは`ドライバーA`〜とする
- 業種は「精密機械」「化学品」「食品」等の架空ラベルに留め、それ以上特定できる情報を持たせない。**運用者本人の実際の勤務先の強み業界とは意図的に一致させない**(2026-08-04、公開前チェックで指摘・修正。当初は勤務先の強み業界と同一の業種名を使っており再識別リスクがあった)
- 所属企業・営業所が特定できる地名の組み合わせを使わない
- コスト単価・原価率・採算水準はすべて合成値であり、実績とは無関係であることをREADMEと画面上に明記する
- 公開前に `pre-publish-anonymization-check` スキルを通す

## 6.5 実装時に判明した設計上の要点

実装して初めて分かった、設計書だけでは見えなかった2点を記録する。

### (a) 運賃を実コストから逆算してはいけない

初期実装では売上を「実コスト × マークアップ」で作っていた。この場合、拘束時間が伸びても燃費が悪化しても売上が連動して上がるため、**仕込んだ赤字パターンが粗利に現れない**。

現実の運賃は計画上のコース諸元に基づいて事前に合意されるものであり、実績の悪化はキャリア側が被る。だからこそ荷待ちが問題になる。修正後は標準原価(計画距離・公称燃費・標準拘束時間・契約時点の燃料単価)から運賃を決め、実績との差が粗利に効くようにした。回帰テストで固定している。

### (b) 全社中央値との比較では主因を切り分けられない

`拘束時間/km` や `運賃/km` を全社中央値と比較する方式では、**Lv3の的中率がLv1を下回った(45.8% < 50.0%)**。

原因は、これらの指標が距離に構造的に依存すること。荷役時間は距離によらずほぼ一定なので、短距離コースほど時間/kmが大きくなる。全社中央値と比べると「短距離である」ことを「拘束時間が長い」と誤判定する。

各コース自身の諸元(距離・車格)から**構造的に期待される水準**を基準にする方式へ変更し、91.7%まで改善した。距離の違いを性能の違いと読み違えない、というのが要点。

### (c) 案件単価の基準原価から人件費・高速代を漏らすと全コースが恒常的赤字になる

`trip_orders`実装時、案件単価の基準となる「標準原価」を燃料費+減価償却だけで組んだところ、原価の実に4割程度にしかならず、**マークアップを乗せても実コスト(人件費・高速代を含む)を賄えず全24コースが例外なく赤字**になった。人件費は原価の中で最も大きい構成要素であり、これを外すと単価計算そのものが成立しない。`generate_trips()`が`revenue_yen`(荷主目線モデル)の算出で使っている標準原価の式(燃料費+人件費+減価償却+高速代)と同じ構成に揃えて修正した。2つの独立した収益モデル(`revenue_yen`と`trip_orders`)を作る際は、**片方で確立済みの原価構成をもう片方でも省略せず踏襲する**ことを教訓として残す。

## 9. この設計で答えられるようになる問い

設計の妥当性は「どんな問いに答えられるか」で判断する。

- **今の情報量では何が判断できず、何が見えれば判断できるようになるのか**(L1.5)
- **赤字コースの主因は4パターンのどれか。よって交渉相手は荷主か、他部署か**(L1.5)
- どのコースが赤字か。赤字の原因は運賃か、積載率か、ドライバーの燃費か
- 軽油が10円/L上がったら営業利益はいくら減るか。その影響はどこに集中しているか
- 燃料高騰を積載率の改善で打ち返せるか。打ち返せないならいくらの値上げが必要か
- 売上上位の顧客は、採算も良いのか
- 次に運賃交渉すべき顧客はどこか。いくら要求すべきで、その根拠は何か
- 協力会社への支払いは適正原価を下回っていないか(v0.1の支払い側モードの発展)
